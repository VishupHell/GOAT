# Проектные решения безопасности «КоЗа»

Решения относятся к [паспорту проекта](PROJECT.md), [требованиям безопасности](SRs.md) и [модели угроз](Ts.md). Они описывают выбранный способ защиты и планы будущих проверок. Запись проверки ниже не означает, что тест уже выполнен.

**Состояние на момент подготовки:** в запускаемой технической основе есть модели и часть API, но регистрация и вход ещё планируются. Некоторые действующие маршруты принимают `admin_id`, `author_id` или `user_id` из тела запроса и пока не проверяют полномочия по подтверждённой сессии. Поэтому решения D-01–D-03 следует реализовать и проверить по мере развития приложения; текущий `/health` подтверждает запуск, а не выполнение этих решений.

## D-01. Подтверждённая личность и актуальное членство при доступе к команде

**Контекст.** Клиент может подставить чужой `userId` или `role`, запросить задачу по известному ID либо сохранить действующую сессию после удаления из команды. Идентификаторы и заявления клиента не подтверждают его личность и доступ к данным команды.

**Решение.** После входа сервер устанавливает действующего пользователя из проверенной им сессии. Для защищённого запроса без такой сессии сервер отказывает. При обращении к задаче сервер получает её `team_id` из сохранённой записи, а не принимает принадлежность задачи со слов клиента. Перед выдачей данных или продолжением операции сервер проверяет в хранилище текущее членство установленного пользователя в этой команде. Указанные в запросе `userId` и `role` не используются для определения действующего лица и его прав. Членство не считается бессрочно подтверждённым только потому, что при входе в систему оно существовало.

**Обоснование.** Серверу нужны два разных факта: кто делает запрос и имеет ли этот человек доступ к конкретной команде сейчас. Проверка актуального состава отзывает доступ после удаления участника даже тогда, когда его сессия ещё действительна. Проверка команды, к которой относится задача, исключает чтение чужой задачи по известному ID.

**Связанные угрозы:** T-01, T-04, T-09, T-10.

**Связанные требования:** SR-01, SR-04, SR-09, SR-10.

**Будущая проверка:**

- **Условие:** есть команды X и Y, задача X, участник A команды X и пользователь B вне X; у A и B действующие сессии.
- **Действие:** B запрашивает задачу X по её ID. Затем администратор удаляет A из X, и A повторяет чтение задачи со своей прежней сессией. Отдельно выполняется создание команды без сессии с чужим `userId` в запросе.
- **Ожидаемый результат:** задача X не выдаётся ни B, ни удалённому A; команда без подтверждённой личности не создаётся. Добавление `userId` или `role=admin` в запрос не меняет результат.

**Ограничения и последствия.** Проверка актуального членства требует обращения к хранилищу при защищённых запросах. Если позже появится кеш прав, его придётся обновлять или обходить при отзыве членства. Механизм входа и сессий ещё не реализован; до его появления выполнение D-01 не подтверждено. В SR-04 критерий приёмки пока говорит о «незарегистрированном» пользователе, хотя само требование — об «авторизованном»: критерий следует уточнить для запроса без действующей сессии.

## D-02. Разрешение конкретного действия над задачей

**Контекст.** Членство в команде даёт возможность читать её задачи, но не разрешает создавать их, менять чужой статус, назначать постороннего исполнителя или удалять задачи. Проверка только наличия пользователя в команде не различает эти действия.

**Решение.** Перед изменением задачи сервер устанавливает действующего пользователя по D-01, загружает целевую задачу и её команду из хранилища и проверяет право на запрошенное действие:

- создать задачу может администратор указанной команды; назначаемый исполнитель должен быть её действующим участником;
- изменить статус существующей задачи может назначенный исполнитель либо администратор этой команды в рамках правил продукта; исполнитель не получает права менять её описание и назначение;
- изменить описание или исполнителя может администратор команды; нового исполнителя также проверяют по текущему составу команды;
- удалить задачу может администратор её команды, если функция удаления остаётся в продукте.

Если право отсутствует или назначение недопустимо, сервер отклоняет запрос до сохранения изменений. `author_id` и другие поля тела запроса не подтверждают право действовать от имени указанного человека.

**Обоснование.** Решение принимается на сервере по фактическим данным задачи, назначенного исполнителя и команды. Это разделяет право видеть задачу и право менять её состояние, а также сохраняет назначение исполнителя внутри команды.

**Связанные угрозы:** T-02, T-03, T-07, T-08.

**Связанные требования:** SR-02, SR-03, SR-07, SR-08.

**Будущая проверка:**

- **Условие:** в команде X есть администратор A, участники B и C; задача назначена B. Пользователь Y состоит только в другой команде.
- **Действие:** C пытается изменить статус задачи B и создать задачу X. A пытается создать задачу X с исполнителем Y. Затем B меняет статус своей задачи допустимым способом.
- **Ожидаемый результат:** первые три запроса отклоняются без изменения задач; разрешённый запрос B меняет статус. Если удаление задач реализовано, попытка C удалить задачу также отклоняется без её удаления.

**Ограничения и последствия.** Изменение и удаление существующих задач в паспорте указаны как функции, которые можно исключить. Если удаление исключается, следует одновременно убрать SR-07, T-07 и соответствующий пункт D-02. Текущая основа уже проверяет членство назначаемого исполнителя при некоторых операциях, но остальные перечисленные проверки прав пока не подтверждены.

## D-03. Управление составом только в пределах своей команды

**Контекст.** Участник команды может напрямую вызвать маршрут добавления или удаления человека, а администратор другой команды — передать чужой `team_id`. Неразрешённое изменение состава влияет на доступ к задачам и возможность выполнять работу.

**Решение.** Перед созданием приглашения или добавлением участника, а также перед удалением участника сервер устанавливает действующего пользователя по D-01 и сверяет его с администратором именно той команды, состав которой меняется. При отсутствии такого права состав не меняется. Успешное удаление сохраняется в хранилище до ответа об успехе. На каждом следующем запросе удалённого пользователя D-01 проверяет уже обновлённый состав; прежняя сессия сама по себе не возвращает ему доступ.

**Обоснование.** Администратор X управляет составом X, но не Y. Проверка перед записью защищает состав от обычного участника и администратора чужой команды; проверка состава после записи обеспечивает отзыв доступа.

**Связанные угрозы:** T-05, T-06, T-09, T-10.

**Связанные требования:** SR-05, SR-06, SR-09, SR-10.

**Будущая проверка:**

- **Условие:** A — администратор X, B — участник X, C — администратор другой команды Y; у B есть назначенная задача X.
- **Действие:** B пытается добавить или пригласить нового участника и удалить коллегу из X; C пытается удалить участника X. Затем A удаляет B, после чего B со своей прежней сессией запрашивает задачу X и пытается изменить её статус.
- **Ожидаемый результат:** действия B и C по изменению состава отклоняются, состав X остаётся прежним. Удаление B администратором A сохраняется; последующие чтение задачи и изменение статуса от B отклоняются.

**Ограничения и последствия.** Сейчас API напрямую добавляет участника через `POST /teams/{id}/members`, а паспорт описывает приглашение и его принятие. До реализации нужно выбрать и согласовать один порядок вступления в команду; проверка прав администратора требуется в обоих вариантах. После удаления назначенного исполнителя задача остаётся в системе, но этому пользователю больше нельзя предоставлять доступ к ней; правило её переназначения нужно отдельно определить в предметной логике.
